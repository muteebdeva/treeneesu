# Treeneesu — Release Process

How a Treeneesu release is cut, verified, and published. Written for
the maintainer; every step is checkable by a reviewer.

## 1. Versioning

- Version format: `vMAJOR.MINOR.PATCH` with pre-release suffixes
  (`-rcN`) until a release gate set is fully met. The current line is
  `v0.1.0-rc1` — the `0.x` and `rc` markers are load-bearing: they say
  "experimental", per AUDIT-PRODUCTION-READINESS.md verdict B.
- A version number may only be attached (git tag in the source clone +
  GitHub Release) by the owner's explicit decision. Preparing release
  notes does not publish a release.

## 2. Pre-release checklist

1. Working tree clean; source clone HEAD identified by full hash.
2. Clean build from the exact tree (fresh build directory) — exit 0.
3. Full unit suite — all suites pass; log saved under `logs/`.
4. Functional subset (`test/functional/test_runner.py` list in
   TEST-SUMMARY.json) — all pass.
5. Sanitizer subsets (ASan + UBSan, 12 suites) — zero reports.
6. Secret scan of the full tree (patterns: private-key headers,
   `wallet.dat`, `.env`, token assignments) — zero hits.
7. `PRODUCTION-DIFF.patch` regenerated and eyeballed end-to-end:
   `git -C bitcoin-core diff <upstream-base>..HEAD -- <production paths>`.
8. Docs reconciled: TEST-SUMMARY.json describes *this* build's runs,
   not a previous one's.
9. If the release serves a live network: refresh
   `nMinimumChainWork` per §3; if it introduces the public testnet,
   apply the seed-hostname step per §4.

## 3. nMinimumChainWork maintenance (F-03)

Rule (THREAT-MODEL.md §6): the value is read from the designated
chain, never invented.

```
python3 tools/min-chain-work.py \
  --cli "bitcoin-cli -datadir=<synced node datadir> -rpcport=29332" \
  --safety-blocks 100
```

Paste its full provenance output (tip height/hash, anchor height/hash,
value) into the release notes, set the constant in
`src/kernel/chainparams.cpp`, rebuild, and re-run the full unit suite
(the value is sanity-checked by `pow_tests` chain sanity only for
internal consistency — the *provenance* is the release notes' job).

## 4. Public-testnet seed step (F-04, owner-gated)

Only when the infrastructure in `deploy/README.md` is **actually
provisioned and verified** (seed nodes syncing, DNS resolving):

1. In `src/kernel/chainparams.cpp` (CMainParams), set the DNS seed to
   the real hostname (search marker `OWNER-SEED-HOSTNAME`).
2. Treat this as a consensus-identity change: full rebuild, full unit
   suite, functional subset, fresh two-node verification that a
   default-flags node now discovers the seed set.
3. Record hostname, seed IPs, and verification output in the release
   notes. Until this step is performed, every document must keep
   saying the network has no bootstrap.

## 5. Artifacts, checksums, signing

- Release artifacts are built from the tagged tree only:
  `bitcoind`, `bitcoin-cli`, `test_bitcoin` ( Linux x86-64 at minimum).
- Publish `SHA256SUMS` alongside the artifacts:
  `sha256sum bitcoind bitcoin-cli test_bitcoin > SHA256SUMS`.
- Signing: the owner signs `SHA256SUMS` with their own OpenPGP key
  (`gpg --detach-sign --armor SHA256SUMS`) and publishes the public
  key fingerprint in the repository README. **No signing key is ever
  stored in this repository or generated by an agent.** If no owner
  key exists, the release is published unsigned and the release notes
  must say so.
- Reproducibility status, stated honestly: two builds of the same tree
  on the same machine have produced identical *behaviour*; **bit-for-bit
  reproducible (Guix) builds are not yet established** for Treeneesu.
  Do not claim them. The verification path is: build from source and
  compare `getblockhash 0` + the test suite, per FINAL-REPORT.md.

## 6. Upgrade policy

- Parameter changes (anything in the 5 production files) are
  chain-defining: they create an incompatible network unless they are
  pure additions (e.g., the §4 seed step or a §3 chain-work bump,
  which only affect node *policy* at sync time). Release notes must
  state which kind a release is.
- There is no auto-update. Operators upgrade by replacing binaries and
  restarting; chain state in the datadir is preserved by upstream's
  versioning.
- A vulnerability fix follows SECURITY.md: fix on the source branch,
  expedited release, disclosure after the fix is available.
